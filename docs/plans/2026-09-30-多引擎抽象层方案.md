## 1. 背景

当前 LlamaLens 只支持 llama.cpp `llama-server`。问题不是缺少一个 SGLang poller，而是 `llama.cpp` 的采集、状态、事件、告警、API 字段和前端组件已经耦合到各层。

要支持 SGLang，并后续支持 vLLM，需要引入一层 Engine Adapter，把引擎差异收敛在采集/适配层内，上层只消费统一状态。

## 2. 目标

### 2.1 需求

- 增加中间层，屏蔽底层推理引擎差异。
- 第一期支持 SGLang。
- 保留现有 llama.cpp 监控能力，不回归。
- 为后续 vLLM 扩展预留结构。

### 2.2 验收标准

- `hosts.yaml` 可按主机声明引擎类型：`llama_cpp` / `sglang`。
- 旧 `llama:` 配置仍然可用，默认映射为 `llama_cpp`。
- 后端 `HostMonitor` / API / WS 不直接依赖 llama.cpp 的 `/slots`、`/props`、日志正则等细节。
- SGLang 主机可展示：
  - 在线状态
  - 模型路径 / 模型名 / 上下文或 KV 容量
  - 生成速度 tok/s
  - prompt 处理速度 tok/s（如指标可得）
  - 上下文 / KV cache 占用
  - running / queued 请求数
  - GPU / CPU / 内存 / 磁盘 / 网络 / 进程 / systemd 服务
  - 历史趋势
  - 事件流
- SGLang 不支持的 llama.cpp 专属项（MTP、slot 明细）不硬造数据，只隐藏或降级展示。
- 不新增写操作、不控制推理服务、不提交真实凭证。
- 文档、example、README 同步。

### 2.3 非目标（第一期）

- 不实现 vLLM。
- 不修改 Go CLI / TUI。
- 不做推理服务控制：不 abort、不 flush、不改配置。
- 不做用户认证 / 多租户。
- 不做历史数据持久化。
- 不改变单进程部署形态。
- 不强制 SGLang 必须有 SSH；但第一期主机级 GPU/CPU/内存/进程监控仍依赖 SSH。

## 3. 当前实现

### 3.1 后端

- `backend/monitor.py`
  - `HostMonitor` 直接创建 `LlamaPoller`、`SshPoller`、`LogPoller`。
  - 直接读取 `self.llama.state` 和 `self.log_poller.state`。
  - 速度来源、上下文、slot、MTP 等逻辑围绕 llama.cpp。
- `backend/pollers/llama_api.py`
  - 硬编码 llama.cpp HTTP API：`/slots`、`/props`、`/v1/models`。
  - slot 级速度差分：`n_decoded`、`n_prompt_tokens_processed`、`is_processing`。
- `backend/pollers/log_poller.py`
  - 硬编码 llama-server 日志格式：`print_timing`、`launch_slot_`、`release`、MTP draft acceptance 等。
- `backend/config.py`
  - 有 `LlamaCfg`，`HostConfig` 固定使用 `llama` 配置块。
- `backend/events.py`
  - `llama_up` / `llama_down` / `task_start` / `task_end` / `llama_boot`。
- `backend/alerts.py`
  - `llama` 离线、`ctx`、`mtp` 等告警。
- `backend/api.py`
  - `/api/health` 返回 `llama_online`。
  - overview snapshot 使用 `snap.llama`。

### 3.2 前端

- `frontend/src/views/HostDetailView.vue`
  - 直接依赖 `snap.llama.gen_speed_tps`、`snap.llama.log`、`snap.llama.slots`。
- `frontend/src/components/LlamaStateCard.vue`
  - 展示 llama 日志状态机、MTP、上下文、任务。
- `frontend/src/components/SlotTable.vue`
  - llama slot 明细。
- MTP 接受率卡和 `mtp_acceptance` 趋势图是 llama.cpp 特有指标。
- 门户卡片 `HostCard.vue` 当前主要展示 `host.online`、`gen_speed_tps`、GPU、CPU、内存，这部分较容易引擎无关化。

### 3.3 SSH 主机监控

- `backend/pollers/ssh_host.py` 大部分是通用主机指标：GPU、CPU、内存、磁盘、网络、进程。
- 但进程发现和模型文件探测目前偏 llama：
  - `pgrep -x "{process_name}"`
  - `--model` / `-m` / `--mmproj`
  - 默认进程名 `llama-server`
- SGLang 可能以 `python -m sglang.launch_server` 或容器方式运行，进程名可能是 `python` / `python3`，不能只靠 `pgrep -x python`。

## 4. 根因 / 架构问题

当前问题的根因是：**“推理引擎”没有成为一等抽象**。

llama.cpp 同时出现在：

1. 配置层：`llama` 配置块。
2. 采集层：`LlamaPoller`、`LogPoller`。
3. 状态层：`HostMonitor` 直接读 llama state。
4. 事件层：`llama_up/down`、task state。
5. 告警层：`llama` 离线、MTP。
6. API 层：`snap.llama`。
7. 前端层：`LlamaStateCard`、`SlotTable`、MTP。

要支持 SGLang/vLLM，应该把这些差异收进 engine adapter，而不是继续往上层扩散。

## 6. 方案选型

### 方案 A：Engine Adapter 抽象层（推荐）

新增 `backend/engine/`，把每个引擎的差异封装在 adapter 内。上层 `HostMonitor`、API、WS、前端只消费统一状态。

```text
HostConfig
   │
   ▼
EngineFactory.create(cfg)
   │
   ├── LlamaCppEngine
   │     ├── LlamaPoller
   │     └── LogPoller
   │
   ├── SglangEngine
   │     ├── HTTP /health
   │     ├── HTTP /metrics
   │     ├── HTTP /get_server_info
   │     └── optional LogPoller
   │
   └── future: VllmEngine
   │
   ▼
EngineState（统一状态）
   │
   ▼
HostMonitor → API/WS → Frontend
```

优点：

- 对现有 llama.cpp 代码侵入较小：`LlamaPoller` 和 `LogPoller` 可以先原样保留，包一层 `LlamaCppEngine`。
- SGLang 的 API、日志、指标差异都收敛在 `SglangEngine`。
- 后续 vLLM 只需要新增 adapter。
- 上层不需要知道 `/slots`、`/metrics`、`print_timing` 等细节。
- 前端可以逐步从 `snap.llama` 迁到 `snap.engine`。

缺点：

- 需要新增一层抽象，短期代码量增加。
- 需要定义清楚统一数据模型。
- SGLang 与 llama.cpp 的指标语义不完全一致，UI 上需要区分“上下文占用”到底是 slot context 还是 KV cache usage。

### 方案 B：在 HostMonitor 里按 engine if/else

优点：

- 改动看起来少。

缺点：

- `HostMonitor` 会变成大杂烩。
- SGLang/vLLM 继续污染 monitor、events、alerts、API、前端。
- 后续每加一个引擎都更乱。

不推荐。

### 方案 C：全部改成 Prometheus-only

即每个引擎只暴露 `/metrics`，面板只读 Prometheus。

优点：

- 指标统一，接入简单。

缺点：

- llama.cpp 当前没有稳定 `/metrics`，且现有 slot/日志任务状态很丰富。
- SGLang 的 `/metrics` 也不能完全替代 llama.cpp 的 slot 明细和 MTP。
- 会损失当前已有能力。

不推荐作为第一期方案。

## 7. 具体设计

### 7.1 新增 `backend/engine/base.py`

定义统一引擎接口：

```python
class EngineAdapter:
    engine_name: str

    async def start(self) -> None: ...
    def stop(self) -> None: ...

    @property
    def online(self) -> bool:
        raise NotImplementedError

    def state(self) -> Dict[str, Any]:
        """返回统一 engine state。"""
        raise NotImplementedError

    def model(self) -> Dict[str, Any]:
        raise NotImplementedError

    def context(self) -> Dict[str, Any]:
        raise NotImplementedError

    def speeds(self) -> tuple:
        """返回 (gen_speed_tps, prompt_speed_tps)。"""
        raise NotImplementedError

    def requests(self) -> Dict[str, Any]:
        """llama 可返回 slot 摘要；sglang 返回 running/queued。"""
        raise NotImplementedError

    def log_state(self) -> Dict[str, Any]:
        raise NotImplementedError

    def extras(self) -> Dict[str, Any]:
        """引擎专属数据，例如 slots、mtp、server_info。"""
        raise NotImplementedError

    def series_names(self) -> List[str]:
        """该引擎需要写入 llama ring 的序列名。"""
        raise NotImplementedError
```

说明：

- `EngineAdapter` 不直接生成最终 snapshot，只提供统一状态。
- `HostMonitor` 负责把 engine state 和 host metrics 合成 snapshot。
- 事件可以由 engine adapter 调 `EventDetector` 发出，也可以由 `HostMonitor` 根据统一状态发出。第一期建议 adapter 负责引擎内部事件，`HostMonitor` 负责合成和告警。

### 7.3 API 兼容策略

第一期采用 **新字段优先 + 旧字段短期兼容**：

- 新契约：`snap.engine`
- 旧契约：`snap.llama` 暂时保留，只给 llama.cpp 用，或作为兼容别名。
- 前端本期改为读 `snap.engine`，但保留旧字段避免未知外部消费者断裂。

推荐：

```python
snap["engine"] = engine_state
if engine.engine_name == "llama_cpp":
    snap["llama"] = engine_state  # 兼容旧前端/旧消费者
```

SGLang 不伪造 `snap.llama`。等前端完全迁移后，下一版再移除 `snap.llama`。

### 7.4 SGLang Adapter 配置

`hosts.yaml` 示例：

```yaml
hosts:
  - id: sglang-1
    name: SGLang 主机
    engine:
      type: sglang
      host: sglang.lan
      port: 30000
      interval: 1.0
      slow_interval: 30.0
      timeout: 3.0
      health_path: /health
      metrics_path: /metrics
      server_info_path: /get_server_info
      model_info_path: /get_model_info
      # 可选，只有目标 SGLang 启用了鉴权才需要
      api_token: ${SGLANG_API_TOKEN}

    ssh:
      host: sglang.lan
      port: 22
      user: root
      password: ${SGLANG_SSH_PASS}
      interval: 2.0
      keepalive: 15
      timeout: 15.0

    process:
      name: python3
      cmdline_contains: sglang
```

### 7.5 SGLang 采集端点

默认端点：

| 端点 | 频率 | 用途 |
|---|---:|---|
| `/health` | 1s | 在线检测 |
| `/metrics` | 1s | 核心运行指标 |
| `/get_server_info` | 30s | server 配置、max tokens、tp/dp 等 |
| `/get_model_info` 或 `/v1/models` | 30s | 模型信息 |

实际 SGLang 不同版本端点名和字段可能有差异，因此配置里支持覆盖。

### 7.6 SGLang 指标映射

| LlamaLens 统一字段 | SGLang 来源 | 说明 |
|---|---|---|
| `online` | `/health` 200 | 连续 3 次失败判离线 |
| `gen_speed_tps` | `sglang:gen_throughput` 或 `sglang:generation_tokens_total` 差分 | 优先 gauge，其次 counter 差分 |
| `prompt_speed_tps` | `sglang:prompt_tokens_total` 差分 | 无则 `null` |
| `context.used` | `sglang:token_usage` × `max_total_num_tokens`，或等价 used tokens 指标 | 语义是 KV cache 占用 |
| `context.total` | `max_total_num_tokens` / server info | 无则 `null` |
| `requests.running` | `sglang:num_running_requests` | 当前处理中请求 |
| `requests.queued` | `sglang:num_queue_requests` | 排队请求 |
| `requests.max_running` | server info `max_running_requests` | 无则 `null` |
| `model.path` | server info / model info | 模型路径 |
| `model.context_len` | server info / model info | 单请求上下文长度 |
| `model.tp_size` | server info | 展示用 |
| `speed_source` | `metrics` / `diff` | 标明来源 |

注意：

- SGLang 的 `context.used` 不应直接等同于 llama.cpp 的 slot context，它是全局 KV/token 使用量。
- UI 上建议显示为：
  - llama.cpp：`上下文占用`
  - SGLang：`KV/上下文占用`
- MTP 接受率不能硬映射。SGLang 如果没有等价指标，就不展示 MTP 卡，趋势图也不出 MTP。

### 7.7 SGLang 事件

第一期不建议伪造 llama 式 task 事件。

可做：

- `engine_up`
- `engine_down`
- `model_change`
- `error_log`：日志中出现 ERROR / 关键异常
- `queue_warning`：可选，当 queued 超过阈值
- `kv_usage_warning`：复用 ctx 告警

暂不做：

- 精确 `task_start` / `task_end`
- 单请求 token 数
- 单请求耗时
- MTP acceptance

如果后续 SGLang 日志或 metrics 能稳定提供请求级事件，再扩。

### 7.8 SGLang 历史序列

复用现有 `ring_llama`，但序列含义泛化为引擎序列：

- `gen_speed`
- `prompt_speed`
- `ctx_used`
- `mtp_acceptance`：llama 专用，SGLang 不写
- `running_requests`：SGLang 新增
- `queued_requests`：SGLang 新增
- `kv_usage_pct`：可选，SGLang 新增

`HostMonitor.history()` 根据 `engine.series_names()` 输出。

## 8. Llama.cpp Adapter 改造

目标：**先不改现有逻辑，只包一层**。

新增 `backend/engine/llama_cpp.py`：

- 内部持有现有 `LlamaPoller`
- 内部持有现有 `LogPoller`
- 对外暴露统一 `EngineAdapter`
- 将现有 `llama.state`、`log_poller.state` 转成统一 `engine state`

这样第一期风险最低：

- llama.cpp 的 `/slots` 差分逻辑不动。
- 日志状态机不动。
- MTP、slot、task event 不动。
- 只是上层从直接读 `self.llama` 改成读 `self.engine`。

## 9. HostMonitor 改造

当前：

```python
self.llama = LlamaPoller(cfg, self.events)
self.ssh_poller = SshPoller(...)
self.log_poller = LogPoller(...)
```

改造后：

```python
self.engine = EngineFactory.create(cfg, self.events)
self.ssh_poller = SshPoller(...)
```

`_tick_loop` 改为：

```python
gen, prompt = self.engine.speeds()
online = self.engine.online
self.ring_llama.push("gen_speed", now, gen if online else None)
self.ring_llama.push("prompt_speed", now, prompt if online else None)

ctx = self.engine.context()
self.ring_llama.push("ctx_used", now, ctx.get("used") if online else None)

for name in self.engine.series_names():
    value = self.engine.series_value(name)
    if value is not None or online:
        self.ring_llama.push(name, now, value if online else None)

self._snapshot = self._build_snapshot()
```

`_build_snapshot` 改为：

```python
snap = {
    "ts": now,
    "host": {...},
    "engine": self.engine.state(),
    "host_metrics": host_metrics,
    "events": self.events.list(50),
    "alerts": evaluate_alerts(...)
}
```

兼容旧字段可临时保留：

```python
if self.engine.engine_name == "llama_cpp":
    snap["llama"] = snap["engine"]
```

## 10. Events / Alerts 改造

### Events

建议泛化：

| 当前 | 建议 |
|---|---|
| `llama_up` | `engine_up` |
| `llama_down` | `engine_down` |
| `llama_boot` | `engine_boot` 或保留 `llama_boot` 仅 llama |
| `task_start` | 保留，llama 使用 |
| `task_end` | 保留，llama 使用 |
| `model_change` | 保留，通用 |

为了减少前端破坏，事件消息可以写成：

- “llama.cpp 引擎上线”
- “SGLang 引擎离线”

这样用户可读，同时 type 可以统一为 `engine_up` / `engine_down`。

### Alerts

当前：

- `llama` 离线 → danger
- `ctx`
- `mtp`

改造后：

- `engine` 离线 → danger
- `ctx` / `kv_usage`
- SGLang 可选：
  - `queue`
  - `kv_usage`
- llama 保留：
  - `ctx`
  - `mtp`

阈值配置可新增：

```yaml
thresholds:
  queue:
    warn: 16
    danger: 32
  kv_usage:
    warn: 80
    danger: 90
```

为了兼容，SGLang 的 KV 使用率可以继续复用 `ctx` 阈值，同时新增 `kv_usage` 作为更明确字段。

## 11. SSH 进程采集改造

SGLang 进程可能不是简单 `pgrep -x sglang`。

建议 `process` 配置扩展为：

```yaml
process:
  name: python3
  cmdline_contains: sglang
  systemd_unit: sglang.service
```

采集优先级：

1. 如果配置了 `systemd_unit`，先读 `systemctl show -p MainPID`。
2. 如果有 `MainPID`，直接用该 PID。
3. 否则用 `pgrep -x {name}`。
4. 如果仍找不到且配置了 `cmdline_contains`，再用受控方式扫描 `/proc/*/cmdline`。

安全约束：

- `cmdline_contains` 只做固定字符串匹配，不做 shell glob / 正则。
- 不把用户配置直接拼进复杂 shell 表达式。
- 如果值包含空格、引号、路径分隔符等，需要安全转义或拒绝。

模型文件体积：

- llama.cpp：保留现有 `--model` / `--mmproj` 文件体积。
- SGLang：模型通常是目录，不强行 `ls -l` 单文件。第一期可展示路径，不展示 file size，或展示目录名。
- 避免对大模型目录做 `du -sh`，开销不可控。

## 15. 风险

### SGLang 版本差异

SGLang 的 endpoint / metric 名称可能随版本变化。

缓解：

- 端点路径可配置。
- metric 解析做 alias 容错。
- 上线前用目标 SGLang 版本真实 `/metrics` 文本做一次映射校验。

### 指标语义差异

SGLang 的“上下文占用”更接近 KV cache 使用量，不是 llama.cpp 的单 slot context。

缓解：

- UI 文案区分：
  - llama：上下文占用
  - SGLang：KV/上下文占用
- 不硬套 MTP。
- 不展示无法支持的 slot 明细。

### 前端回归

当前前端大量依赖 `snap.llama`。

缓解：

- 第一期保留 `snap.llama` 兼容字段。
- 前端迁移分两步：
  1. 后端新增 `snap.engine`
  2. 前端改读 `snap.engine`，保留 fallback
- llama fixture 必须回归。

### 进程识别风险

SGLang 可能以 `python` 运行，`pgrep -x python` 会误选其他 Python 进程。

缓解：

- 优先 systemd `MainPID`
- 其次 cmdline 固定字符串匹配
- 配置值只允许安全字符，不做 shell 注入

### 性能

`/metrics` 比 `/slots` 可能更重。

缓解：

- SGLang 默认 interval 可配置。
- 如果 1s 压力明显，可临时 2s。
- slow info 30s 刷新。
- 不轮询重接口，不写操作。

### 当前工作区未提交改动

当前 `Dockerfile` 新增 `COPY config/hosts.yaml /app/config`，`.dockerignore` 删除 `config/hosts.yaml`。

风险：

- 真实主机配置可能被打进镜像。
- 与 `.dockerignore` 原安全约定冲突。

建议：

- 实施前先确认这两个改动是否保留。
- 如果本任务要发布，建议还原为“运行时挂载 `config/hosts.yaml`，不打进镜像”。
