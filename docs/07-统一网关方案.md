## 1. 定位与原则

### 1.1 定位

网关是 LlamaLens 的**第三个顶级视角（集群视角）**，一个跨主机的透明统一入口：

- **对外**：一个 OpenAI 兼容端点（`/v1/*`），客户端（Codex CLI / OpenAI SDK / 任意 HTTP）只连它。
- **对内**：按模型亲和路由到具体主机的 llama-server，并做全量治理与观测（审计 / 链路 / 成本 / 鉴权）。

项目由此从"多主机管理"自然演进到"集群管理"，但**主机视角（单主机详情）原封不动**。

### 1.2 核心原则

| 原则 | 说明 |
|---|---|
| 透明不静默降级 | 响应标注 `served_by` / `degraded`；跨模型切换默认关，绝不悄悄换模型 |
| 模型亲和保质量 | 默认按"用户要的模型"路由到装了它的主机，质量不变 |
| 数据面复用 devtools | 规范化 / SSE 透传 / 重试原样保留，**Codex 500 修复能力不丢** |
| 控制面读监控 | 路由决策读 `MonitorRegistry` 实时快照（online / 速度 / ctx / 模型） |
| 内置后端 | 单进程，共享监控数据 / 主机配置 / 鉴权，非独立进程 |

### 1.3 非目标

- 不做跨模型的**静默**负载均衡（LLM 后端异质，输出不可互换）。
- 不改变"以主机为中心"的主机视角。
- 不重写 devtools 已验证的规范化/透传逻辑（只搬不造）。

## 2. 背景：为什么内置、为什么不是 devtools

`devtools/codex_llama_proxy.py`（478 行，纯标准库）已是一个可用的**静态路由网关**，
但它与 LlamaLens 的监控数据是**割裂的**，所以只能"客户端指定主机"，不能"自动选最优"。

| 能力 | devtools 现状 | LlamaLens 后端 |
|---|---|---|
| 路由决策 | 客户端在 model 里写死主机 | `HostMonitor.snapshot()` 有每台实时 online/速度/ctx/模型 |
| 健康摘除 | 无（只靠重试兜底） | 监控天然知道谁在线/谁断连 |
| SSE 代理 | 有（自实现，原样透传） | `playground.py` 已用 httpx 做流式代理 |
| 鉴权 | 无（0.0.0.0 裸奔） | JWT 现成 |
| 治理观测 | 无 | 有历史/事件/效率基础设施 |

**结论**：devtools 证明"代理层这条路是通的"，但它的最大短板（拿不到监控数据）
正是 LlamaLens 后端最强的地方。把网关做进 LlamaLens 后端，才能把两者优势合起来。
devtools 的规范化/透传/重试逻辑作为**数据面核心搬过来**，独立进程退役。

## 3. 数据面（复用 devtools，保基本功能）

> 这是"统一网关不丢最基本功能"的关键。以下能力从 devtools **原样保留**。

### 3.1 请求规范化（Codex 500 修复，原样保留）

`normalize_responses()` 仅作用于 `POST */responses`，其余透传：

- 所有 `system` / `developer` 消息合并为一条 `developer`，置于 `input[0]`
  （修 `Jinja Exception: System message must be at the beginning` 500）。
- `tools` 只保留 `function` 类型；`namespace` 递归展开取其内嵌 function；
  其余类型（`web_search` 等）丢弃；tools 清空时连带移除 `tool_choice`。
- `instructions` / `reasoning` / `function_call` / `function_call_output` 一律不动
  （实测该 llama-server 构建接受 reasoning items，不能剥离）。

### 3.2 SSE 原样透传

- `send_response_only` + 逐块转发，**不解析重封装**（服务外部客户端，要原样回）。
- 与 `playground.py` 的区别：playground 走 `/v1/chat/completions` 且解析后重封装成
  面板自己的 `_sse` 格式（服务面板 UI）。两者并存、互不冲突：
  网关对外用"原样透传"，playground 对内用"解析重封装"。

### 3.3 重试

- 连接级失败 / 上游 5xx → 指数退避 + 抖动（默认 5 次，单次上限 30s，覆盖 llama 重启 ~31s）。
- **不重试**：代理已向客户端开始流式输出后（避免内容重复）；`GET /v1/models`（健康检查）快速失败。

### 3.4 端点

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/v1/responses` | Codex CLI，规范化 + 透传 |
| POST | `/v1/chat/completions` | OpenAI 兼容，透传 |
| GET | `/v1/models` | 聚合所有后端模型清单，id 带 `主机名/` 前缀 |
| * | 其余方法/路径 | 原样透传 |

## 4. 控制面：路由策略（三档）

### 4.1 决策输入

读 `app.state.registry`（`MonitorRegistry`）各主机实时快照：
`llama.online` / `gen_speed_tps` / `prompt_speed_tps` / `ctx` / 模型 / GPU 状态。

### 4.2 三档策略

| 档 | 策略 | 默认 | 质量影响 | 说明 |
|---|---|---|---|---|
| 1 | 模型亲和 | **开** | 无 | 按 model 找"装了它且在线"的主机；用户不用记哪台装了什么。**关 = 模型名不参与路由**，请求走兜底（default 主机 / 任意在线） |
| 2 | 同模型副本 LB | 关 | 无 | 同一模型多台机器（同质）按生成速度**加权随机分流**（速度越快分到的请求越多）；仅档 1 开时有效 |
| 3 | 跨模型降级 | **关** | 有 | 目标模型不可用时降级到"近似模型"；须显式配置 + 响应标注 `served_by`/`degraded`；仅档 1 开时有效 |

- 档 2/档 3 依赖档 1 的模型匹配：UI 上档 1 关闭时档 2/档 3 联动禁用（避免"开着但永不生效"）。
- 档 1 开 + 模型无匹配：**绝不落到兜底主机**（不静默换模型，§13 验收）；档 3 开启且有规则才降级。
- 档 3 是"质量不一致"担忧的解法：**默认关**；要开必须显式配置降级规则，
  且响应透明标注，让调用方知道"我拿到的是谁给的、质量是否变了"。

### 4.3 模型名与主机前缀

- `/v1/models` 返回**逻辑模型名**（basename，跨主机去重，`hosts` 字段列出承载主机）：
  选模型不预设主机，由路由策略（亲和/LB）决策——避免"选模型=定死主机"使 LB 失效。
- `ai.lan/qwen3.8` 仍支持（显式指定主机，devtools 原语义，向后兼容）。
- 无前缀模型名 → 档 1 模型亲和路由（basename 相等或包含，忽略大小写）。

### 4.4 健康摘除

基于监控 `online` 状态，不可用主机自动移出路由池；恢复后自动纳入。
（devtools 只靠重试兜底，这里是主动摘除。）

## 5. 治理与观测（重点）

> 网关稳赚的价值。全部为**旁路能力**，不改变"用户连到哪台"，无质量风险。

### 5.1 鉴权与 API Key 管理

- **面板 UI**：沿用现有 JWT（`get_current_user`）。
- **客户端（Codex 等）**：新增 **API Key**（形如 `ll-xxxx`）。
  - Codex `config.toml` 的 `[model_providers.llamacpp]` 配 `base_url` 指向网关 + 专用 key。
  - 网关端点默认**开鉴权**（改进 devtools 的裸奔）；无有效 key 拒绝。
- **Web 页面 token 管理**（集群视角 → API Keys 区块）：
  - 列表：名称 / key（掩码 + 一键复制）/ 额度(tokens) / 已用(tokens) / 剩余 / 费用 / 状态 / 有效期 / 允许模型。
  - 新建 / 编辑 / 禁用 / 删除：名称、额度（LLM tokens，0=不限）、费用额度、有效期、允许模型白名单。
  - 详情：该 key 的费用趋势、token 用量趋势、最近请求（可下钻链路）。
  - **以 token 维度展示**：额度 / 用量 / 费用均以 LLM tokens 为主计量单位，按 key 分组。

**配额执行机制**（两种配额：`quota_tokens` token 上限、`quota_cost` 费用上限，0=不限）：

- **前置检查**（请求鉴权时）：`used_tokens < quota_tokens` 且 `used_cost < quota_cost`（>0 时）才放行，超了返回 429。
- **后置累计**（请求完成时）：`used_tokens += prompt+completion`、`used_cost += cost`。
- **并发安全**：SQLite 原子自增（`UPDATE ... SET used_tokens = used_tokens + ?`）+ 单写者线程，避免读-改-写竞态，不阻塞事件循环。
- **流式特殊性**：LLM 流式生成，请求开始时未知最终 token 数 → 默认**软配额**（前置近似检查 + 后置累计，可能超发最后一个请求，可接受）；**硬配额**（流中实时累计、超配额中断流）放 P2。
- **维度**：当前按 key 总额度；P2 可扩展时间窗口（每日/每月）与按模型配额。

### 5.2 审计

- 每个请求一条记录（关联 `api_key_id`），字段见 §7 `gateway_requests`。
- 可筛选：按 key / 主机 / 模型 / 时间 / 状态 / 是否降级。

### 5.3 链路追踪（DeepSeek harness 式）

> 比"审计列表"高一层：审计是"一行一条"，链路是"**单个请求从进网关到出网关的完整时间线**"。

- 每个请求一个 **trace**，由若干 **span** 组成（字段见 §7 `gateway_spans`）：

| span | 记录内容 |
|---|---|
| `received` | t0、来源 IP、api_key、请求 model、path |
| `auth` | 鉴权结果（key 有效 / 额度够 / 模型允许） |
| `route` | 候选主机、选中主机、策略（亲和/LB/降级）、是否降级、降级原因 |
| `normalize` | 是否规范化、changes（dropped tools / consolidated system） |
| `forward` | t1、upstream 地址 |
| `ttft` | t2、首 token |
| `done` | t3、completion tokens、usage |
| `retry`（0..n） | 每次重试：attempt、原因、等待时长 |
| `responded` | 最终状态码、总耗时 |

- **UI**：审计列表点某行 → 抽屉展开**瀑布图**（横向时间轴，各 span 一条横条，
  颜色区分 网关/上游/重试/降级），右侧元数据（tokens / 费用 / served_by / 错误）。
- **价值**：请求慢了/错了/被降级了，一眼定位是网关开销、上游 prefill、还是生成慢。
- **实时链路（P2）**：网关用 SSE/WebSocket 推送进行中请求的链路进度（当前阶段 / 已出 tokens）。

### 5.4 成本 / 效率统计

- **两种费用口径**：
  - 电费口径（默认，复用 `efficiency.py`）：`cost = energy_kwh × electricity_price`
    （`energy_kwh = Σ GPU power(W) × Δt / 3.6e6`，电价取 `global.electricity_price`）。
  - token 单价口径（可选）：`gateway.model_prices = {model: price_per_1k}`，
    `cost = (prompt + completion) / 1000 × price`。
- **聚合维度**：按模型 / 主机 / API key / 时间。
- 与现有"效率统计"（tokens/瓦、tokens/天）打通，网关侧补充"按请求 / 按 key"粒度。

### 7.5 性能评估（基于 05 文档实测）

> 复用现有 SQLite（WAL）基础设施与 `HistoryWriter` 模式，不重新造轮子。

**写入**：网关写入频率 = LLM 请求频率（低频，常态 <1 QPS），每请求 ~9 行（1 审计 + ~8 spans）。
对比现有 history 实测（05 §7）：10 主机 15 行/s、批量吞吐 ~21 万行/s、余量 >1 万倍。
网关现实量级（<1 QPS）：审计 30 天 ≈ 260 万行、spans 7 天 ≈ 480 万行，远低于实测 1166 万行无压力线。

**关键**：复用 `HistoryWriter` 的 WAL + 单写者线程 + `executemany` 批量 + 异步队列，
**不阻塞事件循环**；每请求 spans 在结束时一个事务批量插入。

**查询**：
- 链路详情：按 `request_id` 查 ~8 行（索引）→ 毫秒级。
- 审计列表：ts 倒序 + 筛选 + 分页（索引 ts/api_key_id/target_host/status）→ 参考 1h=4.7ms。
- 成本聚合（唯一可能慢）：全表分组求和 → 对策：保留期控制 + **预聚合表**（按天×key×模型，复用 1 分钟聚合思路）+ 步长下推。

**上限与对策**：现实量级无压力；10 QPS 高负载（审计 30 天 ~2500 万行）下开预聚合 +
缩短 spans 保留（7d→3d）+ 仅异常/降级/慢请求留完整链路。

**独立库**：网关用 `data/gateway.db`，不与 `history.db` 共库，避免两 writer 竞争同一写锁。

## 8. 后端结构与挂载

### 8.1 模块划分（新增 `backend/gateway/`）

| 文件 | 职责 |
|---|---|
| `normalize.py` | 从 devtools 搬 `normalize_responses` / `_flatten_tools` / `_item_text` |
| `router.py` | `/v1/*` 端点 + 透传 + 重试 + 鉴权依赖 |
| `routing.py` | 三档路由策略 + 健康摘除（读 `MonitorRegistry`） |
| `trace.py` | span 记录 + 审计写入 |
| `keys.py` | API key 校验 / 额度 / 费用累计 |
| `stats.py` | 成本/效率聚合（复用 `efficiency.py` 口径） |

### 8.2 挂载与关键坑

- `backend/gateway/router.py`，`prefix="/v1"`，在 `create_app()` 里 `include_router`。
- **坑**：`main.py` 的 SPA fallback `@app.get("/{full_path:path}")` 会吃掉所有非
  `api/`、`ws/` 的 GET。网关 `GET /v1/models` **必须在 SPA fallback 之前注册**，
  否则被返回成 `index.html`。→ 网关 router 通过 `include_router` 挂载（在 SPA 定义之前）即可。
- 网关读 `app.state.registry`（`MonitorRegistry`）拿实时快照。
- 端口：默认复用 `:8000` 的 `/v1/*`（单进程单端口，客户端 `base_url = http://panel:8000/v1`）；
  可配置独立端口（兼容 devtools 的 `:8901` 习惯）。

### 8.3 `config.yaml` 新增 `gateway:` 段

```yaml
gateway:
  enabled: true
  default_host: ai.lan
  strategy:
    affinity: true                # 档1 模型亲和（默认开）
    same_model_lb: false          # 档2 同模型 LB（默认关）
    cross_model_fallback: false   # 档3 跨模型降级（默认关）
  fallback_rules: []              # 降级规则（显式配置才生效）
  model_prices: {}                # token 单价口径（可选）{model: price_per_1k}
  audit_retention_days: 30
  trace_retention_days: 7
```

## 12. 风险与对策

| 风险 | 对策 |
|---|---|
| 跨模型降级悄悄降质 | 档 3 默认关；开启须显式配置 + 响应 `served_by`/`degraded` 标注 |
| SPA fallback 吃掉 `/v1/models` | 网关 router 在 SPA 之前 `include_router`；加回归测试 |
| 链路/审计数据膨胀 | 保留期可配 + 定期清理（复用 history 清理机制） |
| 网关成为单点 | 网关无状态（数据在 SQLite + 监控内存），崩溃重启即恢复；可多实例 |
| 搬 devtools 逻辑引入回归 | 规范化用例转回归测试；端到端 Codex 不 500 作为硬验收 |
| 费用口径歧义 | 明确两种口径（电费/token 单价），默认电费（对齐 efficiency） |

## 13. 验收标准

- Codex CLI 经网关（`base_url` 指向 `/v1`）连 llama-server，**不再出现 Jinja 500**，工具调用正常。
- 客户端只连一个入口即可访问多主机模型；`/v1/models` 返回带主机前缀的聚合清单。
- 目标模型不可用时：默认明确报错（不静默切）；开启档 3 后降级且响应标注 `served_by`/`degraded`。
- 集群视角可见：接入信息、路由策略、模型总览、审计 + 链路瀑布图、API Key 管理（额度/费用按 key 维度）。
- 每个请求可在链路里看到 收到→鉴权→路由→规范化→转发→TTFT→完成 全链路，重试/降级节点可见。
- 网关端点无有效 API key 一律拒绝；额度用尽拒绝。
