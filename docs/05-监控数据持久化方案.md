# 监控数据持久化方案

> 现状：监控数据只存内存 RingBuffer（llama @1s / host @2s，各 1 小时），重启即丢；事件流同为内存。
> 目标：重启不丢、可回溯多天、长期保留趋势，且不增加部署复杂度（不引入外部 TSDB）。

## 1. 选型：SQLite（WAL）两级存储

- 与合并方案一致：单进程、零新增服务依赖，数据落 `data/history.db`（Docker 挂卷，与主库 `llama_ctl.db` 分文件，避免监控高频写与管理写互相争锁）。
- 不选 InfluxDB/VictoriaMetrics：多一个容器/进程，违背"单进程 :8000"部署模型。
- 不选纯 JSON 行存储：GPU 卡数动态、序列多，宽表查询更快且无需依赖 JSON1 扩展。

### 1.1 表结构

```sql
-- 一级：原始数据（与内存 RingBuffer 同节奏）
CREATE TABLE ts_llama (              -- @1s，固定 4 序列
  host_id TEXT NOT NULL, ts INTEGER NOT NULL,
  gen_speed REAL, prompt_speed REAL, ctx_used REAL, mtp_acceptance REAL,
  PRIMARY KEY (host_id, ts)
);
CREATE TABLE ts_host (               -- @2s，固定 9 序列 + 动态 GPU
  host_id TEXT NOT NULL, ts INTEGER NOT NULL,
  cpu REAL, mem_used REAL, mem_buff_cache REAL, swap_used REAL,
  net_rx REAL, net_tx REAL, proc_cpu REAL,
  load_1 REAL, load_5 REAL, load_15 REAL,
  gpu TEXT,                          -- JSON: {"0":{util,mem,temp,power},"1":{...}}
  PRIMARY KEY (host_id, ts)
);

-- 二级：1 分钟聚合（长期趋势）
CREATE TABLE ts_llama_1m (
  host_id TEXT NOT NULL, ts INTEGER NOT NULL,
  gen_avg REAL, gen_max REAL, prompt_avg REAL, ctx_max REAL, mtp_avg REAL,
  PRIMARY KEY (host_id, ts)
);
CREATE TABLE ts_host_1m (
  host_id TEXT NOT NULL, ts INTEGER NOT NULL,
  cpu_avg REAL, mem_used_max REAL, swap_used_max REAL,
  net_rx_sum REAL, net_tx_sum REAL, proc_cpu_avg REAL,
  gpu TEXT,                          -- 每卡 avg/max 聚合
  PRIMARY KEY (host_id, ts)
);

-- 事件流持久化（顺带解决事件重启丢失）
CREATE TABLE events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  host_id TEXT NOT NULL, ts INTEGER NOT NULL,
  level TEXT NOT NULL, type TEXT NOT NULL, message TEXT NOT NULL
);
CREATE INDEX idx_events_host_ts ON events(host_id, ts);
```

- GPU 用 JSON 列：卡数因主机而异（1~8 卡），宽表列会稀疏；查询时 Python 侧解析（每行一次，量小）。
- 离线/断点语义保持：值缺失写 NULL（前端 `connectNulls=false` 断点逻辑不变）。

### 1.2 保留策略（可配置）

| 级别 | 节奏 | 默认保留 | 说明 |
|---|---|---|---|
| 原始 | 1s / 2s | 7 天 | 精确回溯（故障定位） |
| 聚合 | 1 分钟 | 90 天 | 长期趋势（容量/利用率规划） |
| 事件 | 实时 | 30 天 | 告警/状态变化审计 |

容量估算（单主机、2 GPU）：原始 ≈ 13 万行/天 → 7 天 + 聚合 90 天，**实测 159MB/主机**（见 §7 基准测试）。

## 2. 写入路径

```
HostMonitor tick（1s/2s，现有逻辑不变）
   │  push RingBuffer（实时/WS 用，不动）
   │  + 组行 → HistoryWriter 内存队列（有界，默认 10000 行，满则丢最旧）
   ▼
HistoryWriter（全局单例，后台任务）
   每 5s 批量 INSERT OR REPLACE（单事务，WAL 模式）
   每分钟：对上一分钟原始数据做 avg/max/sum → 写 *_1m 表
   每小时：DELETE 超出保留期的数据（分批 1 万行/批，避免长锁）
```

- 队列有界 + 批量刷盘：SQLite 写压力 ≈ 每 5s 一次事务（约 130 行/主机），远低于其能力上限；
- 崩溃最多丢最后 5s 未刷盘数据（监控数据可接受）；
- 主机被删除时级联清理其历史数据（`DELETE WHERE host_id=?`，分批）。

## 3. 读取路径

- **实时视图不变**：WS 推送与 1h 内历史仍走内存 RingBuffer（零改动、最快）。
- **`/api/hosts/{id}/history` 扩展**：
  - 现有 `window` 参数保留（300/900/3600 → 内存）；
  - 新增长窗口取值：`14400`(4h) / `86400`(24h) / `604800`(7d) → 查原始表；
  - 超过原始保留期 → 自动降级查 `*_1m` 聚合表（响应中标注 `tier: "1m"`，前端曲线粒度说明）；
  - 统一复用现有 `downsample(600)` + `insert_breaks` 断点逻辑，前端无需感知存储层；
  - Go CLI 只依赖现有参数，向后兼容。
- 查询走 `(host_id, ts)` 主键范围扫描，1 小时窗口 ≈ 5400 行，毫秒级。

## 4. 配置

`config/hosts.yaml` 的 `global` 段（或合并后的全局配置）新增：

```yaml
global:
  history:
    enabled: true
    db_path: data/history.db
    raw_retention_days: 7
    agg_retention_days: 90
    events_retention_days: 30
    flush_interval: 5        # 秒
```

`enabled: false` 时完全退回现状（纯内存），作为回退开关。

## 5. 实施要点

1. 新增 `backend/history.py`（HistoryStore + HistoryWriter），`main.py` lifespan 中初始化/关闭；
2. `monitor.py` tick 中追加一行 `writer.enqueue(...)`（RingBuffer 逻辑不动）；
3. `api.py` history 路由按窗口选层；`events` 路由改为"内存 + 库"合并查询（重启后历史事件可见）；
4. 迁移：无（新功能，老数据不存在）；
5. 测试：写入吞吐（多主机并发）、重启恢复（kill -9 后数据完整度 ≤5s 缺口）、保留期清理、长窗口查询耗时。

## 7. 基准测试（实测）

> 环境：本机 Python 3 + 系统 SQLite（WAL + synchronous=NORMAL），模拟 10 台主机。
> 数据量：7 天原始（1s/2s）+ 90 天 1m 聚合 = **1166 万行**。

**写入**

| 项 | 实测 | 说明 |
|---|---|---|
| 批量灌入吞吐 | ~21 万行/s | 一次性灌 1166 万行耗时 55.6s |
| 实际运行写入 | 1.5 行/s/主机（10 主机 = 15 行/s） | 每 5s 一个批量事务 |
| 余量 | **> 1 万倍** | 写入完全无压力 |

**查询（单主机，history API 场景）**

| 窗口 | 数据层 | 行数 | 实测耗时 |
|---|---|---|---|
| 1h | 原始 | 3,600 | **4.7 ms** |
| 24h | 原始 | 86,400 | 169 ms |
| 7d | 原始步长采样（ts%420=0） | 1,440 | 55 ms |
| 7d | 1m 聚合 | 10,080 | 15 ms |
| 90d | 1m 聚合 | 129,600 | 196 ms |

**其他**

| 项 | 实测 |
|---|---|
| 数据库体积 | 1594 MB / 10 主机 = **159 MB/主机**（7d 原始 + 90d 聚合） |
| 保留期清理（删 1 天 = 12.9 万行） | 916 ms（每小时一次，分批执行无感） |
| 边写边读（200 轮 写 75 行 + 1h 查询） | 0.4s，WAL 下无锁等待 |

**结论**：默认保留策略下，单主机 159MB、写入余量 4 个数量级、常用窗口查询 <200ms，SQLite 无压力。
规模上限参考：50 主机 ≈ 8GB 存储、75 行/s 写入，仍在舒适区；超过 100 主机时建议缩短原始保留期（7d→3d）而非更换存储引擎。
注意：以上为本机磁盘实测，若部署在机械硬盘上，24h 全量扫描（169ms）会变慢，长窗口应走 1m 聚合层（15~196ms）规避。

## 8. 与合并方案的衔接

- 归入实施阶段 **P3（历史持久化）**，位于管理后端（P2）之后、管理前端（P3→P4）之前；
- `data/` 目录、Docker 卷、run.sh 已在合并方案中规划，本方案直接复用；
- 前端后续可加"时间范围选择器"（1h/4h/24h/7d/90d），属 P4 收尾的 UI 增强，非阻塞项。
